## Qué sí hace el código

- `scripts/qa/qa525-vnext-baseline-plan.py` recibe solo objetos Python proporcionados por el caller (NO adapta Docker, no lee disco). Acepta **exactamente** api/web, 5 dependencias `keycloak,postgres,minio,gateway,clamav`, 3 oneshots `db-grants,migrator,minio-init` con `exit_code=0`; imágenes SHA256, IDs de contenedor hex, capas Compose absolutas sin traversal/duplicado y `web_sha` exacto. La estructura `images,dependencies,oneshots,layers,web_sha` coincide con la que consume el verificador Claude #848, pero el módulo no depende de él.
- `prepare(base,target,nonce=...,admission_sha256=...)` valida y copia profundamente ambos, fija SHA256 del JSON canónico para detectar alteraciones accidentales, y devuelve `stage=APPLYING`, `may_apply=false`, `external_runtime_verified=false`; **no** significa que el journal APPLYING esté escrito a disco.
- `advance(plan,stage,proof)` valida etapa anterior y obliga la secuencia `APPLYING → API_SWITCHING → API_VERIFIED → WEB_SWITCHING → WEB_VERIFIED → VERIFYING`. Desde cualquiera de las cinco etapas posteriores a APPLYING puede registrar `ROLLING_BACK → ROLLBACK_VERIFYING` **antes** de iniciar mutaciones de reversión; `RECOVERY_REQUIRED` puede interrumpir todas las etapas y es terminal/bloqueante. No existen escritores APPLIED ni ROLLED_BACK. El proof es un objeto con `kind, stage, nonce, admission_sha256, baseline_sha256, target_sha256, evidence_sha256`, permite detectar vuelos confundidos o reutilización de evidencia, pero **NO autentica quién observó el runtime** ni que ese checksum representa una medición real.
- `tests/test_qa525_vnext_baseline_plan.py` cubre baseline legítimo y variaciones adversariales, ausencia de dependencias/oneshots, capas inválidas, selección de imagen equivocada, replay, pasos saltados y tamper de checksum. Clase importada en readiness protegido. No se usa file/network/subprocess/root/SSH/Docker/host.

## Obstáculos deliberados a instalación

1. Antes de cualquier mutación real, un adaptador revisado bajo locks de host debe capturar el baseline **del mismo host** y una ruta de journal root0600 debe almacenarlo por O_EXCL/fsync fd+dir; una copia en memoria no da crash safety ni protege contra fallo de energía. `qa525-vnext-journal.py` aún no acepta este baseline como parte del registro APPLYING; integration es trabajo futuro.
2. La firma de OPS/artefacto, la decisión Sponsor y G6/restore real del mismo corte se autentican de modo independiente del SHA que el caller suministre. Los módulos #849/#850 no prueban esos actos.
3. Los 5 locks heredados del instalador no están demostrados como dominio de exclusión del ejecutor legacy; se debe deshabilitar legacy, reparar `approval-consumed-*`, validar `dual-<sha>.json` histórico, fijar ambos ancestros confiables, y retener lock ante hijos/cgroups.
4. Claude #848 verifica terminales solo observando adapter. Resultado SHA del verificador tampoco autentica un adapter o un reporte autocreado; no conectar a terminal writer sin target exacto, fuentes confiables, sesiones bajo lock, salud/OIDC y oneshots reales.
5. El código es `prepare/advance` PURO, **NO durable**. No instalar en `glmdch`, no ejecutar Docker ni cambiar main/prod/identidad/DB. QA físico permanece versión `6eed4f00...` último estado operador APPLIED una vez.

**Gate de este PR**: revisión Claude exact-head + CI verde para integrar solamente código inactivo a dev; ninguna activación física. La instrucción Sponsor de máxima aceleración promueve carriles paralelos y revisiones tempranas, no elimina preflight firmado ni autorización de instalación.

## Correcciones tras revisión independiente Claude — mismo paso 3, v2 INACTIVA

Los P2 de revisión del PR #851 identificaron riesgo de mutar rollback sin un paso durable previo y de mezclar planes de distintos vuelos. Se incorporaron etapas explícitas `ROLLING_BACK` y `ROLLBACK_VERIFYING` alcanzables desde API_SWITCHING/API_VERIFIED/WEB_SWITCHING/WEB_VERIFIED/VERIFYING, ligadura `nonce` + `admission_sha256` y proof por etapa/target/baseline/nonce. `MAX_LAYERS=64` para coincidir con el verificador #848. El requisito de archivo Compose base común para API y WEB proviene del contrato `reviewed_layers` de `scripts/qa/operators/qa525-supervised-dual-transaction.py`; el preflight físico deberá verificarlo de nuevo y detenerse si no coincide. La identidad de prueba puede ser autoproducida por un actor malicioso: el checksum del plan NO es firma, no sustituye recepción de prueba validada por el adaptador de runtime.

**Límite deliberado:** el flujo aquí representa exclusivamente una actualización dual API+WEB; rechaza modificaciones WEB-only/API-only como el hotfix 754. La terminal APPLIED o ROLLED_BACK solo podrá ser escrita por el verificador/operador firmado y auditado que compruebe OCI+oneshots+health/OIDC sobre `glmdch` bajo los mismos locks. Un motor futuro tendrá que incluir `nonce,admission_sha256,baseline_sha256,target_sha256` en el journal `APPLYING` escrito con fsync **antes** de cualquier cambio API/WEB. La referencia `proof.evidence_sha256` será vinculada a eventos reales `API_SWITCHED`/`WEB_SWITCHED` de Claude #848 tras su revisión; no se considera auténtica por ser una cadena sha256 bien formada.
